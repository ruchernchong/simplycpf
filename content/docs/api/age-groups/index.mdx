---
title: Age Groups
description: Resolve official CPF bands with inclusive upper bounds
---

CPF contribution bands use inclusive upper ages. Allocation bands split some contribution bands further, so contribution rates and account-allocation rates must not be treated as the same schedule. API v2 exposes `maxAgeInclusive` instead of an ambiguous exclusive maximum.

The next contribution rate applies from the first day of the month after a threshold birthday. Supply `birthMonth` plus `contributionMonth` when exact transition treatment matters; the API returns the applicable thresholds from the effective catalogue schedule.

## GET `/age-groups`

Returns a schedule's contribution and allocation bands with policy provenance. Rates also depend on citizenship and contribution month; use `/calculate` for an exact contribution.

```typescript
interface AgeGroupsResponse {
  contributionMonth: string;
  citizenship: "citizen" | "spr-year1" | "spr-year2" | "spr-year3-plus";
  schedule: { id: string; effectiveFrom: string; effectiveTo: string };
  ageGroups: Array<{
    id: string;
    description: string;
    minAgeExclusive?: number;
    maxAgeInclusive?: number;
    retirementAccount: "SA" | "RA" | "age-dependent";
    retirementRouting:
      | { type: "fixed"; account: "SA" | "RA" }
      | {
          type: "age-dependent";
          thresholdAge: number;
          belowThresholdAccount: "SA";
          atOrAboveThresholdAccount: "RA";
        };
    contributionRate: { employee: number; employer: number };
    allocationRate: {
      OA: number;
      SA?: number;
      RA?: number;
      retirement?: number;
      MA: number;
    };
  }>;
  policy: {
    contribution: PolicyMetadata;
    allocation: PolicyMetadata;
  };
}
```

Following the SA closure, a generic allocation band can cross the SA-to-RA threshold. It therefore returns `retirementAccount: "age-dependent"`, a `retirement` allocation rate, the threshold supplied by policy, and an explicit SA-below-threshold/RA-from-threshold routing object. It does not silently label the whole band SA or RA.

```bash
curl "https://simplycpf.com/api/cpf/age-groups?contributionMonth=2026-08&citizenship=citizen"
```

## GET `/age-group/find`

Supply either completed `age` or `birthMonth`, plus `contributionMonth`. The response flattens the matching group fields and adds `contributionMonth`, `citizenship`, `schedule`, and the same contribution/allocation policy metadata. Because the member's age is known, routing is fixed: a lookup at or above the post-closure threshold returns `retirementAccount: "RA"` and `allocationRate.RA`.

```bash
curl "https://simplycpf.com/api/cpf/age-group/find?birthMonth=1971-08&contributionMonth=2026-08"
```

If both age inputs are supplied, or neither is supplied, the API returns `422`. An unsupported schedule month returns `404`.

## GET `/age/from-birthdate`

Use the deterministic v2 query:

```bash
curl "https://simplycpf.com/api/cpf/age/from-birthdate?birthMonth=1971-08&contributionMonth=2026-08"
```

The response returns `completedAge`, `ageInMonths`, `isBirthdayMonth`, the contribution and allocation band IDs, the month-after-birthday rule, age-only schedule metadata, provenance, and warnings. Explicit month requests use the 24-hour policy cache.

`birthDate=MM/YYYY` remains a deprecated alias for one compatibility cycle. If that path omits `contributionMonth`, the server uses the current Singapore month, includes legacy `birthDate` and `age` fields plus warnings, and returns `private, no-store` because the result is not deterministic. Invalid combinations return `422`; an unsupported policy month returns `404`.

Source: [CPF Board — Which rate applies when an employee enters the next age group?](https://www.cpf.gov.sg/service/article/which-cpf-contribution-rate-should-be-applied-when-my-employee-enters-the-next-age-group). The response's contribution and allocation `PolicyMetadata` records are the canonical effective-period and verification record.
